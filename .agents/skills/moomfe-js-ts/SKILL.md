# 个人 JavaScript / TypeScript 开发习惯

一句话：**先看项目已有写法与工具箱，再按个人默认偏好做最小、清晰、可推导的实现；项目事实永远优先于本 skill。**

本 skill 是个人跨项目习惯，不是 JavaScript / TypeScript 教程。每条规则都应该改变实现选择。Vue / Nuxt 相关决策见 `moomfe-vue`，样式相关见 `moomfe-styling`，这里不重复。

## 规则强度

- **MUST**：必须遵守；除非项目事实明确要求例外。
- **SHOULD**：默认遵守；有明确理由可以偏离。
- **PREFER**：偏好，不是硬规则。
- **AVOID**：通常避免。
- **NEVER**：明确禁止。

## 第 0 步：先看邻居、再看工具箱（MUST）

动手前先完成两件事：

1. **看邻居**：找 1~3 个最相近的既有实现，确认函数形态、命名、导出、类型写法、注释密度和抽象边界。
2. **看工具箱**：确认项目已经提供什么。个人项目优先检查 `mixte`、`@mixte/use`、`type-fest`；宿主项目先确认依赖是否存在，再使用项目自己的工具库与原生能力。

完成判据：

- 新代码的函数、类型、导出和抽象方式都能在现有项目找到参照或明确说明偏离原因；
- 能用现成工具覆盖的逻辑，不计划重新实现；
- 没有为了个人偏好绕过项目已有 formatter / lint / 类型约束。

**兜底**：确实找不到先例时，按本 skill 的默认偏好实现，并在交付说明中注明“无先例可循”。

## 一、怎么写代码

### 函数与参数

- **MUST**：具名函数、导出函数和模块内复用的 helper 优先使用 `function` 声明；箭头函数用于内联回调、JSX 渲染助手和确实需要表达式形态的位置。
- **SHOULD**：参数少而语义清晰；可选配置聚合到 `options`，不要为了省一个对象平铺大量可选参数。
- **SHOULD**：有稳定语义时，优先支持“值或函数”双形态输入；用现有 `isFunction` 等工具分派，不重复造同类判断。
- **SHOULD**：同一语义存在多种稳定调用形态时用重载表达，让调用方保留自然的类型推导；实现签名可以在内部放宽。
- **PREFER**：`defineXxx` 类型推导助手用于“参数保持原样、主要服务类型推导”的场景；`createXxx` 用于真正创建一组结构化能力。

### 控制流与可读性

- **MUST**：优先用早返回压平嵌套；避免三层以上的条件金字塔。
- **SHOULD**：单语句控制流可以省略花括号，多语句块必须使用花括号；最终以项目 formatter / lint 为准。
- **SHOULD**：复杂逻辑用空行和短中文注释分组，说明“这一段为什么存在 / 在完成什么”，不解释语法本身。
- **PREFER**：`??` / `?.`、短路执行、短小三元和中间变量都可以使用；优先可读性，不为了少写一行代码制造聪明表达式。
- **AVOID**：嵌套三元、复杂赋值表达式、长链式 `??`、为了“函数式”而使用复杂 `reduce`。

### 数据与集合

- **SHOULD**：按意图选择遍历方式：转换用 `map` / `filter`，需要顺序 / `await` / `break` / `continue` 用 `for...of`，需要下标或原地调整用经典 `for`，纯副作用可用 `forEach`。
- **AVOID**：普通转换用 `reduce`；确需聚合时才使用，并让累加器类型和意图清楚。
- **SHOULD**：内部状态允许就地修改；跨模块边界、缓存快照或需要隔离的数据再复制。个人工具生态中优先使用 `mixte` 已有的数据处理能力，例如 `toArray`、`deepClone`、`get` / `set` 等。
- **PREFER**：值归一化优先复用现成工具；不要重复实现已经成熟的 `is*`、`to*`、`deep*` 工具。

## 二、怎么设计 TypeScript

### 类型形态

- **MUST**：对象形状优先使用 `interface`；联合、交叉、函数类型、条件类型、映射类型和其他组合型别使用 `type`。
- **SHOULD**：interface 之间优先用 `extends` 组合；只有 interface 表达不自然时才退回 `type` 表达对象形状。
- **SHOULD**：公共 API 的复杂返回和重要契约显式标注；一眼可推导的内部结果依赖推导，不为了“全都写满”而增加类型噪音。
- **SHOULD**：固定取值集合优先用字面量联合，不使用 `enum`。

### 泛型、推导与类型工具

- **SHOULD**：优先让 TypeScript 推导；只有为了公共 API、约束、复用或修正推导边界才增加显式泛型。
- **SHOULD**：泛型有合理默认值时提供默认值，降低调用方负担；不要为了“完美泛型”把调用 API 变复杂。
- **SHOULD**：类型工具优先复用已有依赖。个人工具生态中优先检查 `type-fest`，例如 `Merge`、`Get`、`Paths`、`PickDeep`、`Primitive`、`Promisable`、`PartialDeep`、`AsyncReturnType` 等；依赖不存在时使用原生工具类型。
- **AVOID**：为了 DRY 构造难以阅读的条件类型或类型体操；类型复杂度应该隐藏实现细节，而不是转嫁给调用方。

### any、断言与未知值

- **SHOULD**：动态边界允许使用 `any`，例如动态 body、缓存、重载实现签名、测试构造；不为了“类型纯洁”把所有动态数据改写成多层 `unknown` 收窄。
- **SHOULD**：`as` 用于桥接已有运行时事实或第三方类型；`as unknown as` 只作为确实需要重塑类型的最后手段。
- **SHOULD**：前面已经有明确保证时允许非空断言 `!`；不要用断言替代真正的类型建模。
- **SHOULD**：新代码抑制类型错误优先使用 `@ts-expect-error`，并说明原因；不要新增 `@ts-ignore`。
- **PREFER**：运行时收窄优先使用类型谓词和已有 `is*` 工具；需要强制保证时再提供 `assertXxx` 形式。

## 三、怎么处理异步与错误

- **SHOULD**：默认以 `async` / `await` 表达异步流程；短后处理链可使用 `.then` / `.finally`。
- **SHOULD**：顺序异步循环直接 `for...of` + `await`；只有明确需要并发时才使用 `Promise.all` / `Promise.any` / `Promise.allSettled` 等并发模型。
- **SHOULD**：错误分层处理：参数错误 / 不可能状态直接抛出；封装层记录状态后继续向上抛；边界层负责用户反馈或最终日志；可选数据失败只有在业务明确允许时才吞掉。
- **SHOULD**：需要复位或清理的状态放进 `finally` / `.finally()`。
- **AVOID**：为了形式统一引入自定义 Error 层级、Result / Either 风格封装，除非项目本身已有明确约定。

## 四、怎么设计模块 API 与抽象

### 导出与命名

- **MUST**：源码默认使用具名导出；`export default` 只用于项目 / 框架明确要求 default export 的入口。
- **SHOULD**：应用代码默认不建立 barrel；类库的公共打包入口可以使用 barrel。
- **SHOULD**：命名优先表达语义角色：`is*` / `has*` 判断、`get*` / `set*` 读写、`create*` 工厂、`define*` 推导助手、`init*` 初始化、`map*` / `transform*` 转换、`to*` 转换、`deep*` 深度操作、`random*` 随机能力、`Render*` 渲染助手。
- **PREFER**：同一 API 家族保持词根和返回形态一致，不为了“更好听”频繁换词。

### 参数与返回值

- **SHOULD**：简单、稳定的核心参数优先平铺；选项多且相互独立时使用 `options` 对象。
- **SHOULD**：返回值优先选择调用方最容易理解的形态：单值、结构化对象、元组或 `void`；不要为了“统一”把简单结果包成一层对象。
- **PREFER**：复杂公共 API 的返回类型显式标注；简单内部 helper 依赖推导。

### 抽象阈值

- **MUST**：不要为了目录整洁、减少几行代码或“看起来专业”而创建薄封装。
- **SHOULD**：出现第二个真实使用方、语义已经稳定、类型需要复用、或抽象能够隐藏复杂生命周期 / 状态管理时，再考虑提取。
- **SHOULD**：私有 helper 默认留在当前模块；只有公共语义稳定后才提升到公共 API。
- **AVOID**：同一段逻辑只重复一次就急于抽象；一次性业务逻辑留在原地通常更清晰。

## 反模式

- ❌ 不看项目现有模式就创造新的函数、类型或 API 风格。
- ❌ 导出 `const foo = () => {}` 作为默认的具名 API 形态。
- ❌ 为普通对象形状机械使用 `type X = { ... }`，或为了“高级”堆复杂条件类型。
- ❌ 用 `reduce` 做普通转换。
- ❌ 把所有动态输入都强制改成 `unknown`，或者用断言掩盖真正缺失的类型信息。
- ❌ 不查 `mixte` / `type-fest` 就重写已有能力（前提是项目确实安装了这些依赖）。
- ❌ 应用代码为了统一而大量创建 barrel 或 default export。
- ❌ 为单一调用点创建通用工具。

## 自检清单

提交前逐条过：

1. 看过相邻 1~3 个既有实现，并与它们的函数、类型、导出和抽象方式保持一致？
2. 已检查项目工具箱；现成能力是否已经覆盖了这次需求？
3. 具名 API 是否优先使用 `function`，类型形状和组合类型是否分别落在 `interface` / `type`？
4. 控制流是否足够平，是否为了少写代码制造复杂表达式？
5. `any` / 断言是否停留在合理边界，没有用类型体操制造额外复杂度？
6. 异步并发、错误传播与清理是否符合实际语义？
7. 是否真的值得抽象，而不是因为代码“看起来整齐”？
8. 最终运行项目自己的 lint / typecheck / test。
