# 模块与 API 设计

本文件只讨论“一个能力应该怎样暴露给调用方”。目录结构、具体框架入口和项目约定属于宿主项目 notes，不在这里展开。

## 导出策略

- 默认使用具名导出，方便按语义直接引用。
- `export default` 只用于项目 / 框架明确要求 default export 的入口。
- 应用代码默认不建立 barrel；类库的公共打包入口可以使用 barrel，把内部实现与公共 API 分开。

核心原则：**公共 API 要稳定，内部实现可以自由变化。**

## 命名族

命名优先表达角色，而不是描述实现细节：

| 角色 | 常用前缀 |
| --- | --- |
| 判断 / 谓词 | `is*` / `has*` / `can*` |
| 读写 | `get*` / `set*` |
| 创建能力 | `create*` |
| 类型推导 / 定义助手 | `define*` |
| 初始化 | `init*` |
| 数据转换 | `map*` / `transform*` / `to*` |
| 组合式能力 | `use*` |
| 深度操作 | `deep*` |
| 随机能力 | `random*` |
| 渲染助手 | `Render*` |

同一 API 家族保持同样的词根、参数顺序和返回形态，不要因为个人偏好临时换一套命名。

## define / create

### `define*`

适用于运行时基本不增加行为、主要负责类型推导或描述配置的助手：

```ts
export function defineSomething<T>(value: T): T {
  return value;
}
```

调用方获得更好的类型推导，同时不承担新的运行时抽象。

### `create*`

适用于真正创建一组能力或状态：

- 返回结构化对象；
- 返回元组；
- 返回带附加方法的函数；
- 创建带生命周期的实例。

如果只是为了让一个数组“看起来更规范”，不要创建 `create*`。

## 参数设计

- 核心且稳定的参数优先平铺：`move(array, from, to)`、`pick(object, keys)`。
- 可选配置多、未来可能扩展时使用 `options`。
- 稳定语义可以允许“值或函数”输入，例如 `boolean | (() => boolean)`。
- 不要把一组天然属于同一领域的配置拆成十几个布尔参数。

目标是让调用方**第一次看到函数签名就能写对调用代码**。

## 返回值

优先选择调用方最容易理解的形态：

- 一个明显的结果 → 直接返回值；
- 多个相关结果 → 返回结构化对象；
- 极紧密的固定位置结果 → 可以返回元组；
- 明确是就地操作 → 可以返回原对象，也可以 `void`，跟随同类 API 保持一致。

不要为了“统一响应格式”把所有简单函数都包成 `{ data }`。

## 公共 API 的类型与 JSDoc

公共 API 应该让调用方在编辑器中能够直接理解：

- 参数类型；
- 返回值；
- 默认行为；
- 重要边界；
- 必要示例。

个人类库中可以使用完整 JSDoc（描述、`@param`、`@see`、`@example`）；应用内部只为真正复杂的公共抽象写完整文档，普通 helper 保持简洁。

## 抽象阈值

满足以下任一项，再考虑把局部逻辑提升为公共抽象：

- 第二个真实使用方；
- 语义已经稳定且值得命名；
- 类型需要共享；
- 生命周期、状态或复杂资源管理值得隐藏。

默认策略：

```text
一次性逻辑 → 留在原地
一次重复    → 可以先保留重复
第二个使用方 → 重新评估抽象
稳定公共语义 → 才提升 API
```

不要因为“文件看起来太长”就创建一层空壳 helper。

## 私有 helper 与公共 API

一个 helper 如果只服务当前模块，优先保持私有。只有当调用方开始出现稳定需求时，再提升到公共导出。

这样可以让公共 API 面更小、重构自由度更大。
