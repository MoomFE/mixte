# 组合式函数与组件封装设计

> 触发条件：已经判断需要封装新的组合式函数，或正在设计组件、确定组件 API 与结构时。
> 方法论来源：个人自研库 `@mixte/use`（组合式函数）与 `@mixte/components`（组件库）——个人封装风格的代表作，以下原则均从中提炼。
>
> 边界：`reactivity-patterns.md` 负责回答“这个响应式问题应该怎么实现、是否值得下沉”；本文件只负责回答“既然决定做一个可复用抽象，这个抽象应该怎么设计”。

## 1. 什么时候值得封装

默认不要为了代码整洁创建 composable。

新 composable 至少需要满足以下条件中的一个，并且必须有明确语义：

- 有第二个真实使用方；
- 隐藏了复杂的生命周期 / cleanup / 异步竞态；
- 能形成比直接调用底层 API 更清晰的业务或技术抽象；
- 有稳定的输入、输出协议，而不是把一段局部代码机械搬到 `useXxx`。

一次性业务逻辑默认留在页面 / 组件内。

不要因为以下原因机械抽取：

- 文件变长了；
- 想让目录看起来更整齐；
- 某个函数超过若干行；
- 只是为了给局部逻辑换一个文件。

## 2. 语义化 API

抽象的价值之一是把重复的参数样板提升成稳定语义，让调用方少做配置判断。

例如，已经决定做通用封装后，优先提供语义明确的 API，而不是把底层 options 原样暴露给调用方：

- 条件行为用能直接表达条件语义的 API；
- immediate / deep / scope 等稳定变体，用统一命名表达预设；
- 调用方不应该为了得到常见行为而重复填写同一组 options。

个人库中的 `whenever`、`watchImmediate`、`watchDeep` 等只是这种设计原则的实例；响应式场景下具体选哪个工具，先看 `references/reactivity-patterns.md`。

## 3. 生命周期与 cleanup

如果 composable 注册了监听、事件、定时器、子 watch、effect scope 或缓存引用，封装本身负责保证生命周期正确。

- 能自动跟随当前作用域销毁，就不要把清理责任推给调用方；
- 条件启停的一组副作用，封装内部负责创建、重建与停止；
- 共享缓存使用作用域计数或等价机制时，最后一个引用销毁后应自动清理；
- 存在合理的手动控制需求时，同时提供清晰的 `stop` / `reset` / `clear` 等出口；
- 异步并发需要保证过期结果不会覆盖新结果，不把竞态控制责任推给调用方。

## 4. 输入设计

优先让调用方用最自然的输入形态，内部统一归一化。

- 监听源类参数：与 Vue 的 `WatchSource` 语义一致，接受值 / ref / getter；
- 普通响应式参数：优先使用 `MaybeRefOrGetter<T>` + `toValue()`，让调用方可以传值、ref 或 getter；
- 选项中的单个参数如果本身有响应式需求，也可以接受 `MaybeRefOrGetter<T>`；
- 不要为了追求“万能”而接受无法保持清晰语义的任意输入。

目标不是让 API 什么都能吃，而是让常见调用方式自然、类型安全、无需额外转换。

## 5. 输出工程化

- 默认返回普通对象（状态 + 方法 + 事件钩子），避免 class 或巨型 reactive 对象；
- 需要提供响应式代理变体时，基于同一个内核组合，而不是复制第二份实现；
- 状态命名使用完整、稳定的词汇，如 `isExecuted` / `isLoading` / `isFinished` / `isSuccess`，不随意缩写；
- 事件钩子优先复用项目已有原语（如 vueuse `createEventHook`），注册后返回取消函数；
- 返回值结构保持稳定，避免因为增加一个边缘场景而频繁改变调用方协议。

## 6. 类型推导优先

- 能从输入推导的类型，不要求调用方重复填写；
- 泛型参数应完整贯穿响应、数据、参数元组等相关边界；
- 对响应类型做必要的条件类型推导，从已知类型自动拆出业务数据类型；
- 避免为了“看起来类型完整”要求调用方补大量没有实际价值的泛型；
- 不用 `any` 掩盖无法设计清楚的 API。

`createInjectionState` 之所以优先于手写 `provide/inject`，就是因为它把组件树共享的协议与类型推导一起封装好了。

## 7. 组合而不是重复

新抽象优先由已有原语组合而来，保持单一实现源。

例如：

- 语义化监听工具建立在 Vue `watch` 之上；
- `useRequestReactive` 复用 `useRequest` 的核心实现；
- 组件外壳复用 vueuse / 项目已有 composable，而不是重新实现底层能力。

抽象面向“能力”而不是“当前实现细节”。例如请求封装应该接收请求函数 / 数据源，而不是绑定某一个具体业务接口。

## 8. 组件封装

适用范围：组件封装也遵循“薄壳 + 复用内核 + 清晰协议”的原则。

- **泛型组件**：`<script setup generic="T extends ...">` + `defineProps<Props<T>>()` + `defineSlots<Slots<T>>()`，把类型推导交给调用方；组件类型从 `types.ts` 导出；
- **输入宽松化**：props 接受调用方最顺手的形态，并在内部归一化；不要为了统一内部表示而增加调用方负担；
- **双向绑定用 `defineModel`**：需要区分未传与空值时使用明确的哨兵默认值；
- **命令式 API 用 `defineExpose`**：暴露必要的状态与方法，父级通过模板 ref 调用；
- **插槽协议化**：具名插槽按位置组织；运行态通过明确的 slot props 暴露；字段级动态插槽保持稳定命名；
- **样式钩子而非样式绑架**：提供 class 钩子与布尔开关，不硬编码主题；
- **状态词汇统一**：组件与 composable 共享同一套状态与动作词汇；
- **复用内核**：外壳主要负责 props → 成熟内核 → 状态 / 插槽的协议转换；
- **复杂组件目录**：`index.vue` + `types.ts` + `utils.ts` + `composables/` + `components/` + `css/`；组件私有逻辑放自己的 `composables/`。

## 9. 落地检查

封装完成前逐条过：

1. 是否确实值得形成独立抽象，而不是一次性逻辑换了一个文件？
2. 名字是否表达了语义，调用方是否不再重复填写常见参数样板？
3. 生命周期相关注册是否随作用域正确清理？是否有必要的手动出口？
4. 输入是否兼容项目约定的值 / ref / getter 形态？
5. 输出协议是否稳定、命名是否统一、是否避免巨型对象？
6. 类型能否从输入自动推导？是否存在多余的泛型或 `any`？
7. 实现是否复用了既有原语，而不是复制一套底层逻辑？
8. （组件）props、slots、expose 是否形成清晰协议？
9. （组件）样式是否只留 class 钩子与开关，没有硬编码主题？
